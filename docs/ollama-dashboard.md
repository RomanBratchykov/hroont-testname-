# Inspect Ollama's data-to-dashboard workflow

Every invocation now creates **`run-dashboard.html`**, a standalone visual dashboard. Open the path printed in the `dashboard` result field in your browser. It shows run status, request/tool/issue counts, a chart of context bytes per turn, the supplied task, computed summaries, links to verified generated reports, and an expandable execution timeline. It updates after every recorded stage; refresh the page during a run. No web server or external assets are required. Dry runs also produce a dashboard, clearly labeled **Dry Run**, with no analysis results. Failed runs preserve their visual timeline.

The run dashboard explains the Ollama workflow. Generated climate dashboards contain the rainfall, temperature, heat/frost, dry-spell and coverage charts produced by the existing renderer. Links appear once those files actually exist.

Existing dashboard code:

- `frontend/python/agrodata/report.py`: deterministic, offline HTML dashboard renderer.
- `frontend/python/agrodata/workflow.py`: collection → SQLite → analysis → dashboard/CSV, with persisted run status.
- `frontend/python/agrodata/tools.py`: validated model-facing tool definitions and dispatch.
- `frontend/src/features/personal-state/DemoDashboard.tsx`: the separate, saved example dashboard in the web app. The runner does not edit this screen.

`scripts/ollama_dashboard.py` connects the existing Python tools to local Ollama's `/api/chat`. No new dependencies are needed. Start Ollama and install a model supporting tool calls first. Run from the repository root, replacing `YOUR_MODEL` with its installed model name:

```bash
python3 scripts/ollama_dashboard.py --model YOUR_MODEL --prompt 'Use this synthetic pilot location in Kharkiv Oblast: latitude 49.9935, longitude 36.2304. Collect historical NASA POWER climate for 2016-01-01 through 2025-12-31 using agro_run with sources ["power"], then explain coverage, units, limitations and the dashboard artifact path. This location is a demo, not a verified farmer field.'
```

Collection uses external data services and the existing cache. The coordinates are synthetic; retrieved climate is historical gridded data. Collection currently supports Kharkiv Oblast only. No fallback to a hosted model occurs. Model tool support and local memory determine whether the run succeeds.

To analyze stored data and render a fresh dashboard without collection, supply an actual POWER request ID from a previous run's `sources.power.request_id`:

```bash
python3 scripts/ollama_dashboard.py --model YOUR_MODEL --prompt 'Use existing POWER request_id REPLACE_WITH_REAL_ID. Call agro_analyze, then agro_dashboard. Explain the results, coverage, caveats and output path; do not collect new data.'
```

Use `--db /path/to/agro.sqlite3` if those records are in another database. `--prompt-file task.txt` reads a task from a UTF-8 file. No arbitrary document parsing or model training is performed.

To inspect the exact initial instructions, task, tool schemas and inference settings without contacting Ollama or collecting anything:

```bash
python3 scripts/ollama_dashboard.py --model YOUR_MODEL --prompt 'Analyze the stored request and create a dashboard.' --dry-run
```

Each invocation creates a directory under `data/ollama-dashboard/`:

- `trace.jsonl`: requests sent to Ollama, returned messages, tool arguments/results and errors, flushed after every stage. This is an observable execution trace, not access to the model's internal reasoning. It contains the supplied task and data summaries; keep it private as appropriate.
- `result.json`: final model explanation and tool artifact results. A `completed` status means the model finished its turn; inspect the tool results for failed/partial data collection or absent dashboards.
- `reports/`: dashboard and other artifacts generated by the existing tools. Actual paths are in tool results in the trace.

The runner allows only `agro_run`, `agro_analyze`, `agro_dashboard` and `agro_inspect_run`. Existing schemas validate model arguments; the model cannot select storage paths or execute code. Python computes metrics and renders HTML. The model chooses tools and explains their results. Limits are eight turns by default (maximum twelve), four calls per turn, a bounded context, and a 180-second timeout per model call. Tool errors return to the model; incomplete model responses and exhausted limits fail with a nonzero exit and a trace error. This is a learning harness, not a guarantee that a chosen model will follow every requested step.

You can also create dashboards without any LLM:

```bash
cd frontend/python
python3 -m agrodata run --params examples/run.json
# For an existing stored request, put {"request_id":"ACTUAL_ID"} in analysis.json:
python3 -m agrodata dashboard --params analysis.json --output data/dashboard.html
```

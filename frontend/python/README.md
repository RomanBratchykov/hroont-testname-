# AgroResilience · Python data pipeline

Python виконує збір, збереження, розрахунки та побудову звітів. Модель передає
структуровані параметри й отримує короткий підсумок та шляхи до артефактів.
Модель не потрібна для виконання конвеєра. Поточний React-чат ще не підключено.

## Один запуск від координат до звіту

З `frontend/python`, Python 3.10+:

```sh
python3 -m agrodata run --params examples/run.json
```

У JSON прикладі задано синтетичну пілотну точку Харківської області, 2016–2025 роки,
показники NASA POWER, евристичні пороги та два орієнтовні сезонні вікна.
Результат у stdout містить `run_id`, стан, підсумок, повноту й шляхи до:

- `dashboard.html` — автономний адаптивний звіт з кількома графіками;
- `analysis.json` — повний аналіз за періодами та походження даних;
- `weather.csv` — спостереження для експорту;
- `manifest.json` — результат запуску й статуси джерел.

База за замовчуванням: `data/agro.sqlite3`. Звіти: `data/reports/<run_id>/`.
`--db` і `--reports-dir` змінюють ці шляхи. Артефакти не публікуються в інтернеті.
Дані `data/` та локальне середовище `.venv/` виключено з Git.

## Параметри і прийняті рішення

- Пілот для фермера/агронома: точка та історичні кліматичні показники.
- POWER є єдиним джерелом типового `run`; додаткові джерела вибираються явно.
- Важкі завантаження супутникових файлів запускаються окремо з лімітами.
- Періоди, змінні, пороги, сезонні вікна та блоки звіту задаються JSON.
- Усі розрахунки детерміновані; модель не вигадує показники чи формули.
- Немає автоматичних прогнозів урожайності, цін, прибутку або агрономічного ранжування.
- Відсутні дані залишаються `null`; неповні роки/сезони виключаються з розподілів.
- Календар: UTC. Початок і кінець включні, кінцева дата має передувати сьогоднішній.
- Координати перевіряються за адміністративним полігоном **лише Харківської області (UA-63)**.
  Межа: geoBoundaries / OpenStreetMap / Wambacher, представлений рік 2017.
  Це не кадастрова перевірка й не агрегація даних по полігону поля.
  Точки інших областей і читання старих наборів поза Харківщиною відхиляються.
- SQLite придатний для цього локального сценарію. Мультикористувацьке розгортання,
  автентифікація й черга фонових завдань потребують окремого серверного шару.

## Джерела та рівні обробки

| Джерело | Збір | Обробка |
| --- | --- | --- |
| `power` | Денні спостереження, лише вибрані змінні | Період, повні роки/місяці, сезони, спека, мороз, сухі періоди |
| `soilgrids` | WCS-план; `download` отримує GeoTIFF | `sample-soil`: піксель за координатами, глибина та конверсія одиниць |
| `hls_s30`, `hls_l30` | CMR-гранули й посилання; `download` отримує вибрані канали | `process-hls`: NDVI одного пікселя з Fmask |
| `nasadem`, `srtm` | CMR-гранули й завантаження GeoTIFF/ZIP | `process-dem`: висота й локальний схил за сусідніми пікселями |
| `gpm`, `smap` | CMR-гранули й завантаження файлів | Аналіз внутрішніх значень цих продуктів ще не реалізовано |
| `faostat` | QCL для України, коди культур/показників | Єдиний формат національних річних спостережень |

FAOSTAT current: `FAOSTAT_TOKEN` у середовищі; endpoint з офіційної документації.
Без токена джерело повертає зрозумілу помилку без марного мережевого запиту.
Старий endpoint можна явно вибрати через `options.faostat.service: "legacy"`,
але живі перевірки виявили HTTP 521/таймаут. Поточний endpoint без токена повернув 401.
Статистика України не видається за польові показники чи локальні ціни.

NASADEM/SRTM є статичними даними: дата запиту не обмежує час цих гранул.
CMR: `max_pages` 1–100, по 100 гранул, з дедуплікацією. `possibly_truncated`
означає, що потрібно звузити період або збільшити межу сторінок.
Для іншої версії колекції можна передати перевірений `collection_id` у параметрах джерела.

RUSLE2 і FAO-56 — методики, а не універсальні API. Розрахунків R, LS,
водного балансу й повного RUSLE в цій версії немає; значення не підставляються навмання.

## Окремі команди

```sh
python3 -m agrodata collect --params examples/collect.json
python3 -m agrodata query --params query.json
python3 -m agrodata analyze --params analysis.json
python3 -m agrodata dashboard --params analysis.json --output data/dashboard.html
python3 -m agrodata export-csv --params query.json --output data/export.csv
python3 -m agrodata inspect-run --params run-id.json
python3 -m agrodata tools
```

`query.json`:

```json
{"request_id":"ID_З_COLLECT", "variable":"PRECTOTCORR", "limit":1000, "offset":0}
```

Читання завжди обмежено одним `request_id`: різні точки й часові вибірки
не змішуються. Підтримуються `variable`, `kind`, `start`, `end`, `limit`, `offset`.
Невідомий ID повертає помилку, а не удаваний порожній успішний результат.
`query` має ліміт 1000 за замовчуванням; експорт, аналіз і графіки читають повну
вибірку до 100000 записів та відмовляються мовчки обрізати її на цій межі.

`analysis.json`:

```json
{
  "request_id":"ID_POWER",
  "heat_threshold":35,
  "frost_threshold":0,
  "dry_threshold":1,
  "seasons":[{"name":"Озима пшениця: орієнтовне вікно", "start":"10-01", "end":"06-30"}],
  "cards":["rainfall", "temperature", "heat_frost", "dry_spells", "seasons", "quality"]
}
```

Сезони позначаються роком закінчення/урожаю, озимі переходять через межу року.
Показники потребують `PRECTOTCORR`, `T2M_MAX`, `T2M_MIN`; для температурного
графіка додатково потрібен `T2M`. Сезонні вікна — орієнтовні, не універсальний
календар культури. Лютневий високосний день враховується автоматично.
Крім медіани доступні min/max, p10/p25/p75/p90 та кількість повних років.
Суха серія за місяць обмежена цим місяцем; серія за весь період може переходити між місяцями.

`dashboard` без `variable` створює кліматичний звіт; із `variable` — графік і
таблицю одного показника (зокрема `NDVI` чи `clay:0-5cm`). Усі сторінки працюють
офлайн, екранують текст, мають дані про походження й придатні для друку.
Панельні блоки та періоди вибираються під час генерації, інтерактивного редактора немає.

Усі команди приймають `--params -` для JSON зі stdin. stdout — JSON;
помилки входу — JSON у stderr. `run` зі станом `partial`/`failed` та `collect`
із помилкою джерела повертають код 1. Раніше успішні дані залишаються у БД.

## SoilGrids і HLS

Необов'язкове середовище для растрів:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-raster.txt
```

У вимогах дозволені лише готові бінарні пакети, щоб pip не намагався будувати GDAL.
`requirements-raster.lock.txt` містить версії перевіреного середовища macOS ARM / Python 3.14.

Для ґрунтів спочатку `collect --params examples/soil.json`, потім збережіть
отриманий ID у `assets.json`:

```json
{"request_id":"ID_SOILGRIDS", "max_files":6, "max_bytes":100000000}
```

```sh
python3 -m agrodata download --params assets.json
.venv/bin/python -m agrodata sample-soil --params assets.json
```

Для HLS отримайте CMR-гранули за потрібні дати й виберіть одну гранулу:

```json
{
  "request_id":"ID_HLS_S30",
  "granule_id":"ID_ГРАНУЛИ_З_QUERY",
  "bands":["B04", "B8A", "Fmask"],
  "max_files":3,
  "max_bytes":200000000
}
```

```sh
python3 -m agrodata download --params hls-assets.json
.venv/bin/python -m agrodata process-hls --params hls-assets.json
```

Для L30 замініть `B8A` на `B05`. Потрібні всі три канали однієї гранули
на однаковій сітці. Обчислюється `(NIR - RED) / (NIR + RED)` лише в пікселі
заданих координат. Хмари, тіні, суміжні хмарні пікселі, сніг, вода й високий
аерозоль відкидаються за Fmask; невалідний результат — `null` із прапорцем якості.
Читання вікна 1×1 не завантажує повний растр у пам'ять. Файли каналів потрібно завантажити повністю.
NDVI не визначає автоматично культуру, залишки на полі або врожайність.

Для NASADEM/SRTM після завантаження одного DEM на гранулу:

```sh
.venv/bin/python -m agrodata process-dem --params dem-assets.json
```

Приймаються GeoTIFF та ZIP із єдиним `.hgt`/`.tif`; архів не розпаковується на диск.
Зберігаються `ELEVATION` (м) та `SLOPE` (градуси). Схил — центральна різниця
за вікном 3×3, а не середній схил поля. Для географічної сітки відстані між
пікселями наближені й це позначається прапорцем якості. На краю растра або
за відсутніх сусідніх значень схил залишається `null`. LS не обчислюється.

Завантаження обмежено довіреними HTTPS NASA/ISRIC, кількістю файлів та розміром
кожного файлу. Використовуються атомарний запис і SHA-256; кеш перевіряється за хешем.
HTML/XML-помилки сервісу не зберігаються як растри. Авторизація Earthdata:
`EARTHDATA_TOKEN` у середовищі, ніколи в JSON чи БД. Токен знімається при редиректі.
Деякі схеми входу через перенаправлення потребуватимуть окремого адаптера.
Не розпаковуються сторонні архіви й не виконується код з відповідей API.

## Модельні інструменти

`agrodata.tools.definitions()` повертає JSON Schema інструментів:
`agro_run`, `agro_analyze`, `agro_read`, `agro_dashboard`, `agro_inspect_run`,
`agro_download`, `agro_process`.
Вони не прив'язані до постачальника моделі. Інтегратор викликає:

```python
from agrodata.tools import invoke

result = invoke(
    "agro_run",
    {"latitude":49.9935, "longitude":36.2304, "start":"2024-01-01", "end":"2025-12-31"},
    db="data/agro.sqlite3",
    directory="data/reports",
)
```

Runtime перевіряє типи, вкладені параметри та дозволені значення.
Шляхи до БД/артефактів задає застосунок, а не модель. Довільного SQL, Python
або HTML від моделі немає. `agro_read` обмежено 1000 записами (типово 100).
`agro_run` і `agro_analyze` повертають агрегати; сирі дані залишаються в SQLite/CSV.
Готовий чат або інтеграція з конкретною LLM не входять до цього модуля.

## Збереження та відновлення

- `requests`: параметри, час отримання, URL та сирий JSON.
- `records`: єдиний контракт спостережень і активів, одиниці, походження й якість.
- `files`: локальні файли, контрольні суми, розмір і час завантаження.
- `failures`: історія помилок збору.
- `runs`: стан і результат кожного наскрізного запуску.

Хеш параметрів і версії обробки визначає кеш. Порядок змінних POWER
не створює зайвого запиту. `cache_hours` типово 720; `refresh:true` примусово оновлює.
Оновлення одного джерела атомарне. Невдала спроба не знищує останній успішний
набір; відповідь позначає `stale_available`. Старі дані не підставляються мовчки.
Кеш за повним запитом не є інкрементальним дозбиранням діапазонів, що перекриваються.

## Перевірка

```sh
python3 -m unittest discover -s tests -v
.venv/bin/python -m unittest discover -s tests -v
python3 check_sources.py
```

Перша команда працює без залежностей і пропускає тести растрів.
Друга перевіряє також реальні локальні GeoTIFF: конверсію ґрунтів, NDVI й Fmask.
`check_sources.py` явно робить живі запити й записує `data/source-checks.json`;
не запускається під час звичайних автотестів. Порожній результат каталогу
відрізняється від недоступного сервісу; HTTP 200 не означає, що в точці є придатні знімки.
Фактичні результати перевірок наведено у `VERIFICATION.md`.
